The story behind HelloDoc

01 / The beginning

Where it began

In the rural municipality where I grew up, three villages depended on a health post without a doctor. Accessing healthcare was not always as simple as it should have been. People struggled to understand their symptoms, find reliable guidance, and know where to turn for help.

I kept thinking about a question: what if technology could make that first step toward healthcare easier, even for someone living far from a hospital?

That question became HelloDoc.

Why this mattered to me

The problem was also about information: knowing what a symptom might mean and where to turn when a doctor is far away.

I wanted to use the software skills I was learning to work on a problem I had seen first-hand.

I am not a clinician. HelloDoc is a software project exploring what digital tools can offer, and where professional care remains essential.

Where you live should not decide how easily you can access healthcare.

02 / The build

Building the idea

I wanted to explore how software could bring symptom guidance, doctor discovery, and appointment-related experiences together in one place. HelloDoc became a way to turn that question into an engineering project.

The problem

Recognising barriers to accessing healthcare in underserved communities.

Distance is only one barrier. Uncertainty about symptoms, cost, travel time, and not knowing who to ask all shape whether someone seeks care at all.

The concept

Exploring a digital healthcare platform that combines symptom assessment and access to care.

The idea was never to replace a clinician. It was to make the first step clearer: describe what you feel, get preliminary guidance, and see where to go next.

The engineering

Building a web interface, backend services, and a machine-learning based symptom prediction pipeline.

In practice that meant a static front end, an Express service handling accounts and development routing, and a separate Flask service that loads a saved classifier and its reference datasets.

The next chapter

Improving the experience through better validation, accessibility, and potential real-world collaboration.

These are intentions, not finished work. The honest next steps are evaluation on representative data, usability testing with real people, and conversations with people who deliver care.

03 / The philosophy

Made for people

Doctor assessment form

An approved doctor opens an appointment, then records patient reported symptoms, doctor observed symptoms and free text observations. Only the exact 132 symptom identifiers are sent for prediction; free text stays out of the model and stays in the clinical record.

Routing

Locally, backend/server.js serves the static site and the API, and starts the private Flask service on 127.0.0.1:5001. The Vercel configuration routes /api/* to the Express service and everything else to a static build, but no Python model is deployed there, so prediction routes fail closed until an external model origin is configured.

Private model service

Algo/main.py accepts token protected /internal/assess requests. Its public /predict route returns 403, so the classifier is reachable only from the Express backend. The shared token is read from the environment and never reaches the browser.

Binary feature vector

A dictionary maps each known symptom name to a position. The service builds a zero-filled array of 132 positions and sets a 1 for every recognised symptom, so the model receives a sparse binary vector. Unknown names are rejected before prediction rather than silently ignored.

Saved linear SVC

The vector is handed to a scikit learn Support Vector Classifier loaded from Algo/models/svc.pkl. The shipped model was trained with kernel="linear" and C=1.0, classifies 41 categories, and contains 267 support vectors.

Predicted category

predict() returns the index of one class, which is mapped back to a disease name through a lookup table. Because the model was fitted with probability=False, the service can only report a single label , it has no calibrated confidence score to show.

Dataset rows

The predicted name is used to filter pandas data frames for a description, precautions, medications, diet, and workout guidance. These rows are general reference content, not a prescription or a plan for this patient, and the page labels them as requiring clinician review.

Assessment record and PDF

Express stores the prediction beside the doctor's own assessment and plan. The assessment page reloads that stored record, and the PDF is generated from the same row. The model output cannot be edited; editing symptoms creates a new revision and leaves the earlier prediction unchanged.

Express authentication

/api/auth/signup, /login, /recover and /logout call Supabase Auth with the public key, then set HTTP-only session cookies. State changing requests also require the trusted application origin. The browser never receives a Supabase key or a service role secret.

Supabase Auth and profiles

Supabase stores credentials and the profiles table, which carries the role, suspension flag and doctor verification status. Row level security scopes appointments, assessments and notes to the signed in patient, doctor or administrator.

Step 1 of 4 · Symptoms

Technical disclosure. The current implementation uses a saved SVC model for preliminary symptom based classification. Its predictions are not confirmed diagnoses. Clinical accuracy and suitability require independent evaluation and appropriate medical oversight.

One detail worth stating plainly: the training notebook records a held out accuracy of 1.0 on its own 30% test split, and re-running that protocol reproduces both the score and the model's 267 support vectors. A perfect score on a small, highly separable dataset is a sign that the benchmark is easy , not evidence that the tool is clinically accurate. No external or clinical validation has been performed.

Read the implementation

How classification works

Think of it as drawing a line. Every row of training data is a point in space , here, a list of 132 zeros and ones. Each point already carries a label: the disease it belongs to. A classifier's job is to find boundaries that separate points with different labels.

Support vectors. Most training points are far from any sensible boundary; they do not decide where it sits. The points closest to the gap between classes are the ones that fix its position, and they are called support vectors. That is why a model with 4,920 training rows can be described by only 267 support vectors.

Why a linear kernel. A linear kernel searches for straight boundaries. With 132 binary features and 41 classes, the implementation trains one boundary per class in a one versus rest scheme (decision_function_shape="ovr") and returns the strongest match.

What it cannot tell you. This model was fitted with probability=False, so it does not produce calibrated probabilities. You get one label, not a confidence level , which is exactly the kind of uncertainty an interface for real people should be careful about.

Technical detail, if you want it

Frontend structure

The main site is plain HTML, CSS and JavaScript with no build step: shared styling tokens live in Styles/app.css, shared navbar behaviour in Scripts/nav.js, and each page adds its own stylesheet. The doctor assessment page is part of this static site. Older Flask templates remain in Algo/templates but are not served.

Express backend and API responsibilities

backend/production.js exposes the API with no static files, and backend/server.js adds local static serving plus the Flask autostart. Account data, sessions and roles come from Supabase. Database errors are logged by event name and returned as a plain 503 rather than leaking internals.

Flask prediction endpoint

Algo/main.py loads its datasets and the saved model at import time, which keeps request handling fast but makes startup depend on those files being present. Paths are resolved relative to the file itself, not the working directory.

Supabase accounts and row level security

Supabase Auth holds credentials and the profiles table holds role, suspension and verification state. The server uses the public publishable key; the service role key is only accepted by the one time administrator bootstrap script and is never loaded by a web handler.

Authentication mechanisms

Supabase Auth verifies the password and returns a session. Express keeps the access and refresh tokens in httpOnly, SameSite=Lax cookies that are marked Secure when the trusted origin is HTTPS. Login failures do not reveal whether an email exists. Every protected route rechecks the database role, suspension flag and doctor approval.

Model loading and feature encoding

The model is deserialised with pickle at startup. The symptom dictionary and disease list are kept in the same module, so the encoding used at prediction time mirrors the ordering used during training. The saved model expects 132 features and was serialised with an earlier scikit learn release than the one currently pinned, which produces a version warning at load time.

Dataset lookup process

Reference tables are read once into pandas data frames. After a prediction, the helper filters those frames by disease name to assemble the description, precautions, medications, diet and workout sections shown on the assessment page and in the PDF. They describe the dataset row, not this patient, and are labelled as general guidance requiring clinician review.

Deployment architecture

vercel.json declares two services: an Express API and a static web build. Rewrites send /api/* to the API and every other path to the static output. The Flask model is not deployed, so a Vercel environment must point at a separate private model service or prediction routes stay unavailable. This configuration has not been verified on a live Vercel project.
